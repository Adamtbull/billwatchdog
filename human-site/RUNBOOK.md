# BillWatch human pages: integration runbook

How the human pages in `human-site/` go live on the existing Cloudflare Pages project behind getbillwatchdog.com. Nothing in this pull request has been deployed, no Cloudflare setting has been changed, and no secret is involved. Every step that touches Cloudflare needs Adam's go-ahead.

What gets added to the live site:

- one worker module, `dist/billwatch-human.mjs` (generated from `src/`, no imports, no network access, no prices), pasted into `_worker.js`
- the dispatch lines at the top of the `_worker.js` fetch handler, plus a one-line homepage switch, applied by `integration/billwatch_human_patch.py` so a rebuild cannot drop them
- two static files, `/assets/billwatch-human.css` and `/assets/billwatch-human.js`
- nine entries in the `_routes.json` include list (and possibly one exclude, see section 4)
- one D1 database, bound to the Pages project as `BILLWATCH_CLICKS`

What does not change: `/v1/*`, `/mcp`, `/api/*`, `/api`, `/demo`, `/plans`, `/llms.txt`, `/agent.json`, `/.well-known/agent.json`, the privacy and disclosure pages, and, while the switch is off, `/`. For any path the human pages do not own, the new call returns `null` before it touches a binding or reads the request body, so the existing dispatch receives exactly the request it receives today.

## 0. Before you start

Confirmed against the live files in review (2026-10-10):

- `_worker.js` (about 48 KB) has a single `export default`, and its fetch order is `/api/events`, then `/api/agent-report` and `/mcp-log.html`, then `/mcp`, then `counted()` for everything else. It defines no `BillWatchHuman` or `HUMAN_HOMEPAGE` (the patch script also checks `humanResponse`).
- `_worker.js` is generated by `build/make_worker.py` from `build/deploy/functions/`, and the site is deployed by a dashboard or API zip upload, which does not process a `functions/` folder and does not bundle imports. So: paste the module inline, and apply the patch with the script in section 3a, never by hand.
- `_routes.json` has 21 include rules and no excludes, and `"/"` is included.
- `plans.html` exists (served at `/plans`). Nothing exists at `/vpn`, `/streaming`, `/compare`, `/go` or `/affiliate-disclosure`, and there is no `_redirects` file.
- `counted()` records aggregate daily counts by area in the existing `BW_COUNTS` D1 database, through `waitUntil`.

Re-check before integrating, in case something changed since:

1. Work from the live site's source, which this repository does not contain.
2. The output folder must not contain anything named `vpn`, `vpn.html`, `streaming`, `streaming.html`, `compare`, `affiliate-disclosure`, `affiliate-disclosure.html` or `go`, and there must be no `_redirects` rule for those paths. If something is there, stop: the new routes would shadow it. `plans.html` is expected and is fine (section 4).
3. Count the rules in `_routes.json` (include plus exclude). After this change it must still be 100 or fewer, and each rule 100 characters or fewer.

## 1. Create the click-count database (D1)

Do this first. Until the binding exists, every `/go/` link answers 503 instead of redirecting. This is a separate database from `BW_COUNTS`, so click counts stay apart from the agent traffic statistics.

Dashboard route (no terminal needed):

1. Cloudflare dashboard, **Storage & databases > D1 SQL database > Create database** ([direct link](https://dash.cloudflare.com/?to=/:account/workers/d1)).
2. Name: `billwatch-clicks`. Location: **Eastern North America (ENAM)**. Select **Create**.
   Why set the location: without a hint, D1 places the database near whoever creates it, which for Adam means Oceania. The site lists US plans, so most clicks are likely to come from the US, and each click waits for the database write before it redirects. Western North America (WNAM) is also fine.
3. Open `billwatch-clicks` and select **Console**. Paste the full contents of `human-site/migrations/0001_clicks.sql` and select **Execute**.
4. In the same console, run:
   ```sql
   SELECT name FROM sqlite_master WHERE type = 'table' AND name = 'click_counts';
   ```
   Expected: one row, `click_counts`.
5. **Workers & Pages >** the BillWatch Pages project **> Settings > Bindings > Add > D1 database bindings**. Variable name: `BILLWATCH_CLICKS`. D1 database: `billwatch-clicks`. Save it for the **Production** environment.
6. Preview environment, pick one:
   - bind a second database, `billwatch-clicks-preview`, created and migrated the same way, so test clicks never touch production counts (recommended), or
   - leave Preview unbound, in which case preview `/go/` links answer 503 by design.
7. A new binding takes effect on the next deployment.

Terminal route (same result, needs Node and a Cloudflare login):

```sh
npx wrangler@latest d1 create billwatch-clicks --location=enam
npx wrangler@latest d1 execute billwatch-clicks --remote --file=human-site/migrations/0001_clicks.sql
npx wrangler@latest d1 execute billwatch-clicks --remote --command="SELECT name FROM sqlite_master WHERE type = 'table' AND name = 'click_counts';"
```

Then add the binding in the dashboard as in step 5. Do not add a `wrangler.toml` (or `wrangler.json`) to the Pages project to declare it: for Pages, that file becomes the source of truth for the project's bindings and settings, replacing what the dashboard holds.

The migration uses `CREATE TABLE IF NOT EXISTS`, so running it again, or later through `wrangler d1 migrations apply`, is harmless.

How it behaves once bound:

- `GET /go/{plan-id}` adds 1 to that plan's count for the current UTC day, then answers 302 to the provider's plain page (no query string, no affiliate code). `HEAD` answers the same 302 without counting.
- Without the binding, `/go/` answers 503 "Provider links are unavailable because durable click recording is not configured." If the write fails, it answers 503 too. It never redirects without a confirmed write.
- Counts are redirect requests, not visitors or sales. Read them in the console:
  ```sql
  SELECT day, plan_id, click_count FROM click_counts ORDER BY day DESC, click_count DESC;
  ```

## 3. Add the human pages to `_worker.js`

### 3a. Rebuild-safe: the patch script (use this for getbillwatchdog.com)

`_worker.js` is generated by `build/make_worker.py`, so a hand edit to it would be wiped by the next rebuild. Instead, `billwatch_human_patch.py` applies the integration to the built file, every time:

1. Make it the last step of `build/make_worker.py`, so it cannot be forgotten. After the line that writes `_worker.js`, add:
   ```python
   import subprocess, sys
   from pathlib import Path
   subprocess.run([sys.executable, str(Path(__file__).parent / "human" / "billwatch_human_patch.py"), str(WORKER_PATH)], check=True)
   ```
   `WORKER_PATH` stands for whatever path `make_worker.py` writes `_worker.js` to. The script path is found relative to `make_worker.py` itself, so it works from any folder. With `check=True`, a refusal from the script stops the build instead of leaving a worker without the human pages. If you would rather not touch `make_worker.py`, run the same command by hand after every rebuild:
   ```sh
   python3 build/human/billwatch_human_patch.py path/to/_worker.js
   ```
2. Before every upload, confirm the built worker includes the human pages. This writes nothing:
   ```sh
   python3 build/human/billwatch_human_patch.py --check path/to/_worker.js
   ```

What the script does:

- It pastes `billwatch-human.mjs` inline just above `export default`, so the zip upload needs no imports, and it adds the dispatch lines as the first lines of `async fetch(...)`, using the worker's own parameter names.
- It removes its own earlier output first, so running it again, or after every rebuild, gives the same file. `--remove` takes the human pages back out and restores the exact original bytes.
- It refuses, without writing anything, if the worker does not have exactly one `export default` and one `async fetch(...)` line, if `BillWatchHuman`, `HUMAN_HOMEPAGE` or `humanResponse` already appear in it (for example a leftover hand patch), or if the bundle is not the generated file.
- It keeps the worker's line endings and needs only Python 3 (no packages, no network).

### 3b. The same change by hand (for a hand-maintained `_worker.js`)

Not for getbillwatchdog.com, whose worker is generated. The script produces the equivalent of these two additions.

At the top of the file:

<!-- worker-patch:top -->
```js
import { BillWatchHuman } from "./billwatch-human.mjs";

// Homepage switch. false: "/" keeps today's agent homepage. true: "/" serves the new human homepage.
const HUMAN_HOMEPAGE = false;
```

As the first lines inside `fetch`, before the existing `const { pathname } = new URL(request.url);`:

<!-- worker-patch:fetch -->
```js
    const humanResponse = await BillWatchHuman.handleHumanRequest(request, env, ctx, { homepage: HUMAN_HOMEPAGE });
    if (humanResponse) return humanResponse;
```

The result:

```js
import { BillWatchHuman } from "./billwatch-human.mjs";

// Homepage switch. false: "/" keeps today's agent homepage. true: "/" serves the new human homepage.
const HUMAN_HOMEPAGE = false;

export default {
  async fetch(request, env, ctx) {
    const humanResponse = await BillWatchHuman.handleHumanRequest(request, env, ctx, { homepage: HUMAN_HOMEPAGE });
    if (humanResponse) return humanResponse;
    const { pathname } = new URL(request.url);
    if (pathname === "/api/events") { /* unchanged */ }
    if (pathname === "/api/agent-report" || pathname === "/mcp-log.html") { /* unchanged */ }
    if (pathname === "/mcp") { /* unchanged */ }
    return counted(request, env, ctx);
  },
};
```

- The import works when `_worker.js` is bundled by `wrangler pages deploy` (module next to `_worker.js`) or is a `_worker.js/` folder (module inside it). For an unbundled upload, replace the `import` line with the whole of `dist/billwatch-human.mjs` except its last line, `export { BillWatchHuman };`.
- Everything the module adds sits inside one constant, `BillWatchHuman`, so it cannot collide with other names in `_worker.js`.

### Why existing routes stay byte-identical

- For a path it does not own, `handleHumanRequest` returns `null` after one pathname check. It does not touch `env.ASSETS`, `BILLWATCH_CLICKS` or any other binding, and it does not read the request body, so `/mcp` POSTs and `/api/events` reach their handlers intact. The test suite patches a stand-in of this dispatch both ways (3a and 3b) and compares status, headers, body bytes and side effects for every existing route, with the switch off and on.
- Human routes never reach `counted()`, so human page views and the human pages' own data reads stay out of the agent traffic statistics.
- An error on a human route ends in a 500 or 503 from the human layer. It never falls through to the existing handlers.

## 4. Add the human routes to `_routes.json`

Append these nine entries to the end of `include`. Keep every existing `include` entry, leave `exclude` as it is apart from the one conditional entry below, and do not add `/*`.

```json
"/vpn", "/vpn/", "/streaming", "/streaming/", "/plans/*", "/compare/*", "/affiliate-disclosure", "/affiliate-disclosure/", "/go/*"
```

Then the one conditional entry, because `plans.html` exists:

- If `"/plans"` is **already** in `include`, add nothing more. `/plans` already runs the worker, and the human handler returns `null` for it (it only owns `/plans/{id}/`), so the existing page is served exactly as today.
- If `"/plans"` is **not** in `include`, also add `"/plans"` to `exclude`. `"/plans/*"` can match bare `/plans` as well (Wrangler's matcher does), which would start sending `/plans` through the worker and into `counted()`. The page would look the same, but `counted()` would begin recording it. The exclude keeps `/plans` exactly as today, and `/plans/{id}/` still reaches the worker. `_routes.json` has no "exact match wins" rule; `exclude` beats `include`.

Shape of the result (illustrative, existing entries abbreviated):

```text
{
  "version": 1,
  "include": [ "/", "/demo", "/api", "/v1/*", "/mcp", <every other existing entry, unchanged>,
               "/vpn", "/vpn/", "/streaming", "/streaming/", "/plans/*", "/compare/*",
               "/affiliate-disclosure", "/affiliate-disclosure/", "/go/*" ],
  "exclude": [ "/plans" ]      <- only if "/plans" is not in include
}
```

- `"/"` must already be in `include` (it is). The homepage switch relies on it, and no change is needed.
- Both spellings, with and without the trailing slash, are listed so the rule holds whether or not the matcher treats the slash as optional. Wrangler's local matcher does; the extra entries cost nothing.
- Other paths under the new prefixes that the human pages do not own, such as `/compare`, `/go` or `/plans/Upper-Case/`, have no page today. They now run the worker, get `null`, and fall through to `counted()`, ending in the same 404 as before.
- `human-site/integration/routes-include.json` holds the same lists in machine-readable form.

## 5. The homepage switch

The open product decision is kept to one line. For getbillwatchdog.com it lives in `build/human/billwatch_human_patch.py`, because `_worker.js` is regenerated:

```python
HUMAN_HOMEPAGE = False
```

(For a hand-maintained worker, it is the `const HUMAN_HOMEPAGE = false;` line in `_worker.js`.)

- `False` (what this pull request ships): `/` is untouched. The human pages live at `/vpn/`, `/streaming/`, `/plans/{id}/`, `/compare/nordvpn-vs-surfshark/`, `/compare/netflix-vs-hulu/` and `/affiliate-disclosure/`. Nothing on the current homepage links to them yet.
- `True`: `/` serves the human homepage (lowest verified VPN and streaming prices, links to the tables, and a small "Building with an agent?" link to `/api`). The current agent homepage is no longer reachable at `/`, and `/` stops passing through `counted()`, so whatever `counted()` records for homepage visits stops too.

Changing it is a one-line edit, a rebuild and a redeploy. To try the human homepage in a preview without changing the line, run the script with `--homepage on` for that build only.

## 6. Preview, verify, then production

1. Deploy to a preview first, with the switch off. Build the preview from the same source as the current production deployment plus these changes, so the data files match. Run the `--check` command from section 3a on the built `_worker.js` before uploading.
2. Compare existing routes, byte for byte, from any machine with Node 22.13 or later:
   ```sh
   node human-site/scripts/compare-existing-routes.mjs https://getbillwatchdog.com https://<preview>.pages.dev
   ```
   It sends only GET, HEAD and OPTIONS to existing read-only routes. It never requests `/go/`, never POSTs to `/mcp`, and identifies itself with the User-Agent `billwatch-integration-check` so `counted()` can tell its reads apart. Expected: `No differences`. If the only differences are headers that your zone adds to the custom domain, rerun it with the production `https://<project>.pages.dev` address as the first argument. With the switch on, add `--skip-home`.
3. Open the human pages on the preview: `/vpn/`, `/streaming/`, a plan page (any "Details & history" link), both comparisons and `/affiliate-disclosure/`. Each should show prices with source-check dates. A page saying prices are temporarily unavailable means the worker could not read `/v1/deals.json` through `env.ASSETS`. Also open `/plans` and check it is the existing plans page.
4. Click flow on the preview: with a preview database bound, a "Get deal" button should land on the provider's site, and the console should show a count of 1 for that plan today. With Preview unbound, expect the 503 message instead.
5. Production only with Adam's approval. Afterwards, `curl -sI https://getbillwatchdog.com/go/<plan-id>` should show `302` and a `location` header. `HEAD` never counts. A 503 means the binding is missing. Without a terminal, open `https://getbillwatchdog.com/go/<plan-id>` in a browser instead: it should land on the provider's site, and it adds 1 to that plan's count for the day.

## Rollback

- Fastest: Pages dashboard, the project, **Deployments**, the previous production deployment, **Rollback**.
- Homepage only: set the switch back to `False`, rebuild and redeploy.
- Full: run `python3 build/human/billwatch_human_patch.py --remove path/to/_worker.js` (or restore the saved copy), remove the patch-script call from `make_worker.py`, restore the saved `_routes.json`, delete the two asset files, redeploy, and rerun the comparison script.
- Leave the D1 database and its binding in place unless deleting them is separately approved. Without the code nothing uses them.

## Reference

Data path. The pages read `/v1/deals.json` and `/v1/price-history/{plan-id}.json`, the same files agents get, through `env.ASSETS`. There is no network request, so no self-subrequest back through the worker, and no dependency on the project's compatibility date. No price is written in the code; every figure comes from that feed at request time.

| Situation | What a visitor gets |
| --- | --- |
| `env.ASSETS` missing, or `/v1/deals.json` unreadable or invalid | 503 page: prices temporarily unavailable, nothing estimated |
| Price history file missing or invalid | Plan page renders, history marked unavailable |
| Unknown plan or comparison | 404 page |
| `/go/` without `BILLWATCH_CLICKS`, or a failed write | 503 text, no redirect |
| `/go/` for a plan without a plain, non-affiliate provider URL | 503 text, no redirect |
| Unexpected error on a human route | 500 text, no fall-through |

Load. Each human page view and each `/go/` click runs the worker once. On the Workers Free plan those requests share the daily allowance with `/mcp` and the counted routes. Rendering with the current 65-plan feed measured about 2 ms of CPU or less per page locally (Node 22, warm), well inside the Workers Free per-request CPU limit. Pasted, the module adds about 42 KB to `_worker.js`.
